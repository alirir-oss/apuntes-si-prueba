# 5. Permisos en Linux: UGO avanzado y ACL

En la Unidad 3 (apartado 2.7) aprendiste los permisos básicos `rwx` y la orden `chmod`. Ese modelo se llama **UGO** porque distingue tres clases de usuarios: el propietario (*User*), el grupo (*Group*) y el resto (*Others*). En este apartado lo completas con:

- El cambio de **propietario** y de **grupo** de los ficheros.
- La **máscara** que decide los permisos de los ficheros nuevos.
- Los **permisos especiales** SUID, SGID y *sticky bit*.
- Las **listas de control de acceso** (ACL), que superan las limitaciones del modelo UGO.

## 5.1 Repaso: cómo decide Linux si tienes permiso

Cuando un proceso intenta acceder a un fichero, el sistema comprueba **en este orden** y se detiene en la **primera** coincidencia:

1. Si el usuario es **root**, se permite el acceso (salvo ejecutar un fichero que no tenga ningún permiso `x`).
2. Si el usuario es el **propietario**, se aplican los permisos de `u`.
3. Si el usuario pertenece al **grupo** del fichero, se aplican los permisos de `g`.
4. En otro caso, se aplican los permisos de `o`.

> [!NOTE]
> Como se aplica solo la primera coincidencia, un propietario con permisos `---` **no** puede leer su fichero aunque el grupo o el resto sí tengan permiso. Es poco habitual, pero demuestra que los permisos no se suman.

Recuerda también que, para borrar o renombrar un fichero, lo que importa es el permiso de **escritura en el directorio** que lo contiene, no los permisos del propio fichero.

## 5.2 Cambiar propietario y grupo: `chown` y `chgrp`

| Orden | Función |
| --- | --- |
| `chown usuario fichero` | Cambia el propietario. |
| `chown usuario:grupo fichero` | Cambia el propietario y el grupo a la vez. |
| `chown :grupo fichero` | Cambia solo el grupo. |
| `chgrp grupo fichero` | Cambia solo el grupo. |
| `-R` | Recursivo: aplica el cambio a un directorio y todo su contenido. |

```bash
sudo chown ana informe.txt              # El propietario pasa a ser ana
sudo chown ana:dam1 informe.txt         # Propietario ana y grupo dam1
sudo chown -R miapp:miapp /opt/miapp    # Toda la aplicación pertenece a su usuario de servicio
chgrp dam1 practica.sh                  # Un usuario puede cambiar el grupo a uno de SUS grupos
```

Solo **root** puede cambiar el propietario de un fichero. El propietario puede cambiar el grupo, pero solo a uno de los grupos a los que pertenece.

## 5.3 Permisos por defecto: `umask`

Cuando un programa crea un fichero, solicita unos permisos iniciales: normalmente `666` (`rw-rw-rw-`) para los ficheros y `777` (`rwxrwxrwx`) para los directorios. La **máscara** (`umask`) indica qué permisos se **quitan** de esos valores iniciales.

```text
Permisos finales = permisos iniciales  SIN  los bits que estén a 1 en la máscara
```

| `umask` | Ficheros (desde 666) | Directorios (desde 777) | Uso típico |
| --- | --- | --- | --- |
| `022` | `644` `rw-r--r--` | `755` `rwxr-xr-x` | root y servidores: todos pueden leer, solo el propietario escribe. |
| `002` | `664` `rw-rw-r--` | `775` `rwxrwxr-x` | Trabajo en grupo: el grupo también puede escribir. |
| `027` | `640` `rw-r-----` | `750` `rwxr-x---` | El resto de usuarios no puede ni leer. |
| `077` | `600` `rw-------` | `700` `rwx------` | Máxima privacidad. |

> [!IMPORTANT]
> La máscara **no es una resta aritmética**: indica qué bits se eliminan. Con `umask 033`, los ficheros quedan con `644` (no con `633`), porque a `rw-` no se le puede quitar una `x` que no tenía. Además, la máscara **nunca añade** permisos: un fichero nuevo nunca tendrá permiso de ejecución por mucho que cambies la máscara; se le da después con `chmod +x`.

```bash
umask              # Muestra la máscara actual en octal (0002)
umask -S           # La muestra en notación simbólica (u=rwx,g=rwx,o=rx)
umask 027          # Cambia la máscara SOLO para esta shell y sus procesos hijos
touch prueba && mkdir dir_prueba && ls -ld prueba dir_prueba
# -rw-r----- ... prueba
# drwxr-x--- ... dir_prueba
```

Para que la máscara sea permanente:

- **Para un usuario**: añade `umask 027` al final de `~/.bashrc` o `~/.profile`.
- **Para todos**: modifica la variable `UMASK` de `/etc/login.defs`, que aplica el módulo PAM `pam_umask` al iniciar sesión.

> [!NOTE]
> En Ubuntu, la máscara habitual de los usuarios normales es `0002`, porque cada usuario tiene su propio **grupo privado** (con su mismo nombre) y nadie más pertenece a él. Para root es `0022`.

## 5.4 Permisos especiales

Además de `rwx`, cada fichero tiene tres bits especiales, que se representan con un **cuarto dígito octal** a la izquierda.

| Permiso | Octal | Sobre un fichero ejecutable | Sobre un directorio | Se ve en `ls -l` |
| --- | --- | --- | --- | --- |
| **SUID** (*Set User ID*) | `4` | El programa se ejecuta con los permisos de su **propietario**, no de quien lo lanza. | Sin efecto. | `s` en la `x` del propietario: `rwsr-xr-x` |
| **SGID** (*Set Group ID*) | `2` | El programa se ejecuta con los permisos de su **grupo**. | Los ficheros que se creen dentro **heredan el grupo del directorio**. | `s` en la `x` del grupo: `rwxrwsr-x` |
| ***Sticky bit*** | `1` | Sin efecto en Linux. | Dentro, cada usuario **solo puede borrar o renombrar sus propios ficheros**, aunque tenga permiso de escritura en el directorio. | `t` en la `x` del resto: `rwxrwxrwt` |

Si el permiso especial está activo pero el `x` correspondiente no, la letra aparece en **mayúscula** (`S` o `T`), lo que normalmente indica un error de configuración.

### Ejemplos reales

```bash
ls -l /usr/bin/passwd
# -rwsr-xr-x 1 root root ... /usr/bin/passwd
```

`passwd` tiene **SUID** y su propietario es root. Por eso un usuario normal puede cambiar su contraseña, aunque eso implica escribir en `/etc/shadow`, un fichero que solo root puede modificar.

```bash
ls -ld /tmp
# drwxrwxrwt 20 root root ... /tmp
```

`/tmp` tiene permisos `777` para que todos puedan crear ficheros temporales, y el ***sticky bit*** impide que un usuario borre los ficheros de otro.

### Asignar permisos especiales

```bash
chmod u+s programa         # SUID           (octal: chmod 4755 programa)
chmod g+s directorio       # SGID           (octal: chmod 2775 directorio)
chmod +t directorio        # Sticky bit     (octal: chmod 1777 directorio)
chmod 3770 compartido      # SGID + sticky (2 + 1) y permisos rwxrwx---
```

> [!CAUTION]
> Un programa con SUID de root es un **riesgo de seguridad**: si tiene un fallo, un atacante puede aprovecharlo para conseguir privilegios de administrador. Nunca pongas SUID a scripts ni a programas que no lo necesiten. Revisar qué programas tienen SUID es una tarea habitual de auditoría:
>
> ```bash
> sudo find / -xdev -perm -4000 -type f -ls 2>/dev/null
> ```

### Caso práctico: directorio de proyecto compartido

Queremos que los miembros del grupo `dam1` trabajen juntos en `/srv/proyecto`: todos pueden crear y modificar ficheros, nadie más puede entrar, y nadie puede borrar los ficheros de otro.

```bash
sudo mkdir -p /srv/proyecto
sudo chown root:dam1 /srv/proyecto
sudo chmod 3770 /srv/proyecto     # 2 = SGID (heredar grupo) + 1 = sticky; rwx para root y dam1
ls -ld /srv/proyecto
# drwxrws--T 2 root dam1 ... /srv/proyecto
```

- Gracias al **SGID**, todo lo que se cree dentro pertenecerá al grupo `dam1` (y no al grupo privado de quien lo crea).
- Gracias al ***sticky bit***, cada usuario solo puede borrar sus propios ficheros. Aparece como `T` mayúscula porque el resto no tiene `x`, lo cual es correcto en este caso: el *sticky bit* solo afecta a los usuarios que pueden escribir en el directorio.
- Para que los compañeros puedan **modificar** los ficheros, estos deben tener permiso de escritura para el grupo: los usuarios deben usar `umask 002` o, mejor, se usa una **ACL por defecto** (apartado 5.6).

## 5.5 Atributos extendidos: `chattr` y `lsattr`

Los sistemas de archivos ext4 (y otros) admiten **atributos** que se aplican incluso a root:

```bash
sudo chattr +i config.ini      # Inmutable: nadie (ni root) puede modificarlo, borrarlo ni renombrarlo
lsattr config.ini              # ----i---------e------- config.ini
sudo chattr -i config.ini      # Quita el atributo
sudo chattr +a registro.log    # Solo añadir (append): se puede escribir al final, pero no borrar contenido
```

## 5.6 Listas de control de acceso (ACL)

### Por qué hacen falta

El modelo UGO solo permite asignar permisos a **un** propietario y a **un** grupo. Imagina que en `/srv/proyecto` (grupo `dam1`) el profesor `marta` necesita **solo leer** y el alumno `pablo`, de otro grupo, necesita **leer y escribir**. Con UGO tendrías que crear grupos nuevos para cada combinación. Las **ACL** (*Access Control Lists*) resuelven el problema: permiten añadir **entradas adicionales** con permisos para usuarios y grupos concretos.

Las ACL de Linux siguen el estándar POSIX y están disponibles en ext4, XFS, Btrfs y la mayoría de sistemas de archivos actuales. Las órdenes `getfacl` y `setfacl` vienen en el paquete `acl`, instalado por defecto en Ubuntu (si no lo está: `sudo apt install acl`).

### Consultar una ACL: `getfacl`

```bash
getfacl /srv/proyecto
```

```text
# file: srv/proyecto
# owner: root
# group: dam1
# flags: -st
user::rwx
group::rwx
other::---
```

Sin entradas extra, la ACL coincide exactamente con los permisos UGO. Cuando un fichero tiene entradas adicionales, `ls -l` muestra un **`+`** al final de los permisos: `drwxrws--T+`.

### Modificar una ACL: `setfacl`

```text
setfacl [opciones] entrada fichero
```

| Opción | Significado |
| --- | --- |
| `-m entrada` | Añade o modifica una entrada (*modify*). |
| `-x entrada` | Elimina una entrada. |
| `-b` | Elimina **todas** las entradas adicionales (vuelve a UGO). |
| `-R` | Recursivo. |
| `-d` | Trabaja con la **ACL por defecto** de un directorio (la que heredarán los ficheros nuevos). |
| `-k` | Elimina la ACL por defecto. |

| Formato de la entrada | Significado |
| --- | --- |
| `u:usuario:permisos` | Permisos para un usuario concreto. |
| `g:grupo:permisos` | Permisos para un grupo concreto. |
| `m::permisos` | Máscara (ver más abajo). |
| `o::permisos` | Permisos del resto. |

```bash
sudo setfacl -m u:marta:rx /srv/proyecto        # marta puede entrar y listar
sudo setfacl -m u:pablo:rwx /srv/proyecto       # pablo, con todos los permisos
sudo setfacl -m g:profesores:rx /srv/proyecto   # El grupo profesores puede leer
getfacl /srv/proyecto
```

```text
user::rwx
user:marta:r-x
user:pablo:rwx
group::rwx
group:profesores:r-x
mask::rwx
other::---
```

```bash
sudo setfacl -x u:pablo /srv/proyecto      # Quita la entrada de pablo
sudo setfacl -b /srv/proyecto              # Quita todas las entradas adicionales
```

### La máscara

Al añadir entradas aparece la línea **`mask`**. La máscara define el **máximo** de permisos que pueden tener las entradas de usuarios concretos, de grupos concretos y del grupo propietario. Los permisos **efectivos** de esas entradas son la intersección entre su entrada y la máscara:

```bash
sudo setfacl -m m::rx /srv/proyecto
getfacl /srv/proyecto
# user:pablo:rwx          #effective:r-x
```

Aunque `pablo` tenga `rwx`, la máscara `r-x` limita sus permisos efectivos a `r-x`.

> [!WARNING]
> En un fichero con ACL, `chmod g=...` **modifica la máscara**, no la entrada `group::`. Por eso, ejecutar `chmod 750` sobre un directorio con ACL puede reducir sin que te des cuenta los permisos de todos los usuarios y grupos adicionales. Revisa siempre con `getfacl` después de usar `chmod`.

### ACL por defecto (herencia)

Las entradas anteriores solo afectan al propio directorio. Para que los **ficheros y subdirectorios que se creen dentro** reciban automáticamente unas entradas, se define una **ACL por defecto** con `-d`:

```bash
sudo setfacl -d -m g:dam1:rwx /srv/proyecto        # Lo nuevo será modificable por dam1
sudo setfacl -d -m g:profesores:rx /srv/proyecto   # …y legible por profesores
getfacl /srv/proyecto | grep default
# default:user::rwx
# default:group::rwx
# default:group:dam1:rwx
# default:group:profesores:r-x
# default:mask::rwx
# default:other::---
```

Si un directorio tiene ACL por defecto, la `umask` **no se aplica** a lo que se cree dentro: los permisos los determina la ACL por defecto. Esto resuelve el problema del caso práctico del apartado 5.4.

> [!TIP]
> Las ACL por defecto solo afectan a lo que se cree **después**. Para aplicar los permisos también a lo que ya existe, combínalas con `-R`:
>
> ```bash
> sudo setfacl -R -m g:dam1:rwX /srv/proyecto      # X mayúscula: x solo en directorios
> sudo setfacl -R -d -m g:dam1:rwX /srv/proyecto   # (y en ficheros que ya fueran ejecutables)
> ```

### Copias de seguridad de las ACL

```bash
getfacl -R /srv/proyecto > acl-proyecto.txt     # Guarda las ACL de todo el árbol
sudo setfacl --restore=acl-proyecto.txt         # Las restaura
```

Al copiar con `cp`, usa `cp -a` (o `cp --preserve=all`) para conservar las ACL. Con `tar`, añade la opción `--acls`.

## Ejercicios resueltos

### Ejercicio 5.1. Calcular con `umask`

¿Qué permisos tendrán un fichero y un directorio nuevos con `umask 026`? ¿Y con `umask 037`?

{{% details "Ver solución" %}}
| `umask` | Fichero (desde `666` = `rw-rw-rw-`) | Directorio (desde `777` = `rwxrwxrwx`) |
| --- | --- | --- |
| `026` (`----w-rw-`) | `640` `rw-r-----` | `751` `rwxr-x--x` |
| `037` (`----wxrwx`) | `640` `rw-r-----` | `740` `rwxr-----` |

En cada posición se eliminan los bits que estén a 1 en la máscara. Por ejemplo, en el fichero con `026`: el grupo tiene `rw-` y la máscara quita `w` (`2`), queda `r--`; el resto tiene `rw-` y la máscara quita `rw` (`6`), queda `---`.
{{% /details %}}

### Ejercicio 5.2. Identificar permisos especiales

Explica cada caso:

1. `-rwsr-xr-x root root /usr/bin/sudo`
2. `drwxrwsr-x root developers /srv/web`
3. `drwxrwxrwt root root /var/tmp`
4. `-rwSr--r-- ana ana notas.txt`

{{% details "Ver solución" %}}
1. **SUID** de root: `sudo` se ejecuta siempre con privilegios de root, que es lo que le permite cambiar de usuario después de comprobar `sudoers`.
2. **SGID** en un directorio: los ficheros que se creen en `/srv/web` pertenecerán al grupo `developers`.
3. ***Sticky bit***: cualquiera puede crear ficheros en `/var/tmp`, pero solo puede borrar los suyos.
4. **SUID sin ejecución** (`S` mayúscula): no tiene ningún efecto, porque el fichero no es ejecutable. Es un error de configuración y se corrige con `chmod u-s notas.txt`.
{{% /details %}}

### Ejercicio 5.3. Directorio de entregas

Crea `/srv/entregas` de forma que:

- Los miembros de `dam1` puedan **dejar** ficheros, pero no **listar** el contenido del directorio ni borrar los ficheros de los compañeros.
- La profesora `marta` pueda ver y leer todo.

{{% details "Ver solución" %}}
```bash
sudo mkdir /srv/entregas
sudo chown marta:dam1 /srv/entregas
sudo chmod 1730 /srv/entregas      # Sticky + rwx para marta, -wx para dam1, nada para el resto
ls -ld /srv/entregas
# drwx-wx--T 2 marta dam1 ... /srv/entregas
```

- El grupo `dam1` tiene `-wx`: puede **crear** ficheros (`w`) y **entrar** (`x`), pero **no listar** el directorio (le falta `r`).
- El ***sticky bit*** impide que un alumno borre o sobrescriba el fichero de otro.
- `marta`, como propietaria, tiene `rwx`.

Para que `marta` pueda **leer** el contenido de las entregas, cada fichero debe tener permiso de lectura para ella. Se consigue con una ACL por defecto:

```bash
sudo setfacl -d -m u:marta:rw /srv/entregas
```
{{% /details %}}

### Ejercicio 5.4. ACL para un caso real

En `/srv/proyecto` (propietario `root`, grupo `dam1`, permisos `2770`):

1. `marta` (grupo `profesores`) debe poder leer todo, incluido lo que se cree en el futuro.
2. `pablo` (alumno de otro grupo) debe poder trabajar como uno más de `dam1`.
3. Comprueba los permisos efectivos y elimina después el acceso de `pablo`.

{{% details "Ver solución" %}}
```bash
# 1. Lectura para marta en lo existente y en lo futuro (X: entrar en directorios)
sudo setfacl -R -m u:marta:rX /srv/proyecto
sudo setfacl -R -d -m u:marta:rX /srv/proyecto

# 2. pablo con los mismos permisos que dam1
sudo setfacl -R -m u:pablo:rwX /srv/proyecto
sudo setfacl -R -d -m u:pablo:rwX /srv/proyecto

# 3. Comprobación y eliminación
getfacl /srv/proyecto
sudo -u pablo touch /srv/proyecto/prueba_pablo     # Debe funcionar
sudo setfacl -R -x u:pablo /srv/proyecto
sudo setfacl -R -d -x u:pablo /srv/proyecto
sudo -u pablo touch /srv/proyecto/otra             # Permiso denegado
```

`sudo -u pablo orden` permite comprobar los permisos de otro usuario sin necesidad de conocer su contraseña.
