# 12. El sistema al servicio del desarrollo

En este último apartado se aplica todo lo anterior a vuestro futuro trabajo: **evaluar qué necesita un equipo** para desarrollar un tipo de aplicación concreto, **prepararlo** correctamente y **desplegar** una aplicación en un servidor siguiendo buenas prácticas de administración. Termina con un **caso práctico integrador** y un **resumen de comandos** de toda la unidad.

## 12.1 Evaluar las necesidades según el tipo de desarrollo

No todos los desarrollos necesitan el mismo equipo. La siguiente tabla es **orientativa**: los requisitos reales dependen del tamaño de los proyectos y cambian con cada versión de las herramientas, por lo que siempre hay que **consultar los requisitos oficiales** de cada una.

| Tipo de desarrollo | Herramientas típicas | Recursos más exigidos | Necesidades del sistema |
| --- | --- | --- | --- |
| **Web (*frontend* y *backend*)** | VS Code, Node.js, Python, Java, bases de datos | RAM moderada, disco SSD | Servidores locales, puertos libres, contenedores. |
| **Móvil Android** | Android Studio, emulador, Gradle | **Mucha RAM**, CPU con varios núcleos, SSD | **Virtualización por hardware** activa para el emulador; espacio para los SDK e imágenes. |
| **Multiplataforma de escritorio** | IntelliJ IDEA, .NET, Qt, Flutter | RAM, CPU | Varios SDK; a veces, máquinas virtuales con otros sistemas para probar. |
| **Contenedores y microservicios** | Docker, Kubernetes local | RAM (cada contenedor consume), disco | Virtualización (Docker Desktop y WSL 2 en Windows), redes virtuales. |
| **Datos e inteligencia artificial** | Python, Jupyter, bibliotecas de cálculo | RAM, **GPU** compatible | Controladores de la GPU, mucho espacio para los conjuntos de datos. |
| **Videojuegos** | Unity, Unreal Engine, Godot | GPU, CPU, RAM | Controladores gráficos actualizados, mucho espacio. |

### Cómo medir si el equipo es suficiente

Las herramientas del apartado 9 sirven para tomar la decisión con datos y no "a ojo". Con el entorno de trabajo abierto (IDE, emulador, contenedores…) y durante una sesión normal de trabajo, observa:

- **Memoria disponible**: si baja de forma habitual por debajo del 10–15 % y aumenta el uso de *swap* o del archivo de paginación, falta RAM.
- **CPU**: si las compilaciones mantienen todos los núcleos al 100 % durante mucho tiempo, una CPU con más núcleos reduciría los tiempos de espera.
- **Disco**: si el tiempo activo del disco está a menudo al 100 % o se usa un disco mecánico, un SSD es la mejora más notable.
- **Espacio**: los SDK, las imágenes de los emuladores, las imágenes de Docker y las dependencias de los proyectos ocupan decenas de gigabytes.

### Comprobar la virtualización por hardware

El emulador de Android, Docker Desktop, WSL 2 y las máquinas virtuales necesitan que la CPU tenga activada la **virtualización por hardware** (Intel VT-x o AMD-V) en la configuración del firmware (UEFI).

```bash
# Linux
lscpu | grep -i virtualiz                    # Virtualización: VT-x  (o AMD-V)
grep -cE 'vmx|svm' /proc/cpuinfo             # Mayor que 0: la CPU la admite
ls -l /dev/kvm                               # Existe si KVM está disponible
```

```powershell
# Windows: también en Administrador de tareas > Rendimiento > CPU > "Virtualización: Habilitado"
(Get-CimInstance Win32_Processor).VirtualizationFirmwareEnabled
```

> [!NOTE]
> Si Windows ya usa el hipervisor (porque están activados Hyper-V, WSL 2 o la seguridad basada en virtualización), `VirtualizationFirmwareEnabled` puede devolver `False` aunque la virtualización funcione. En ese caso, comprueba en el Administrador de tareas si aparece *Hipervisor detectado* o *Virtualización: Habilitado*.

## 12.2 Preparar el equipo de desarrollo

### Una cuenta sin privilegios

Trabaja a diario con una cuenta **estándar** o, en Linux, con tu usuario normal usando `sudo` solo cuando haga falta. Añade tu usuario únicamente a los grupos que realmente necesites (apartado 1.5):

```bash
sudo usermod -aG dialout "$USER"   # Programar placas de desarrollo por el puerto serie
sudo usermod -aG kvm "$USER"       # Aceleración del emulador de Android en Linux
```

> [!CAUTION]
> Pertenecer al grupo `docker` permite, por ejemplo, arrancar un contenedor que monte `/` del anfitrión con permisos de root: **es equivalente a ser administrador**. Añade a ese grupo solo tu usuario, en tu propio equipo, y nunca a usuarios de servicio ni a cuentas compartidas.

### Variables de entorno

Muchas herramientas se localizan mediante variables de entorno, como `PATH` (directorios donde se buscan los programas) o `JAVA_HOME` (instalación de Java).

```bash
# Linux: para tu usuario, en ~/.profile (apartado 3)
export JAVA_HOME=/usr/lib/jvm/java-25-openjdk-amd64
export PATH="$JAVA_HOME/bin:$HOME/.local/bin:$PATH"
```

```powershell
# Windows: variable de usuario permanente (se aplica en las consolas que se abran después)
[Environment]::SetEnvironmentVariable("JAVA_HOME", "C:\Program Files\Java\jdk-25", "User")

# Añadir un directorio al PATH del usuario sin perder lo que ya tiene
$actual = [Environment]::GetEnvironmentVariable("Path", "User")
[Environment]::SetEnvironmentVariable("Path", "$actual;$env:USERPROFILE\herramientas\bin", "User")
```

Gráficamente: `Win + R` > `sysdm.cpl` > *Opciones avanzadas* > **Variables de entorno**. La parte superior contiene las variables del **usuario** y la inferior las del **sistema** (para todos los usuarios; requiere administrador).

> [!WARNING]
> Evita la orden `setx` para modificar el `PATH`: **trunca** los valores de más de 1024 caracteres, y un `PATH` largo puede quedar dañado sin aviso. Usa el método de .NET anterior o la ventana de variables de entorno.

### Ajustes de Windows útiles para desarrollar

| Ajuste | Dónde | Para qué |
| --- | --- | --- |
| **Modo de desarrollador** | *Configuración > Sistema > Para programadores* | Permite crear enlaces simbólicos sin ser administrador, instalar aplicaciones sin firmar de la Tienda y da acceso a otras opciones para desarrolladores. |
| **Directiva de ejecución de PowerShell** | `Set-ExecutionPolicy RemoteSigned -Scope CurrentUser` | Permite ejecutar tus propios scripts; los descargados deben estar firmados (Unidad 3). |
| **Rutas largas** | Valor `LongPathsEnabled` del registro (ver abajo) y `git config --global core.longpaths true` | Evita errores con rutas de más de 260 caracteres (muy habituales en `node_modules`). |
| **Dev Drive** | *Configuración > Sistema > Almacenamiento > Configuración avanzada de almacenamiento > Discos y volúmenes* | Volumen con el sistema de archivos ReFS optimizado para código fuente y compilaciones, con el antivirus en modo de rendimiento. |
| **WSL** | `wsl --install` (Unidad 2) | Disponer de un Linux completo para las herramientas que lo requieren. |

```powershell
# Habilitar las rutas largas en todo el sistema (como administrador; requiere reiniciar)
New-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem" `
                 -Name LongPathsEnabled -Value 1 -PropertyType DWord -Force
```

## 12.3 Desplegar una aplicación en un servidor: buenas prácticas

Cuando tu aplicación pase a un servidor Linux, aplica lo aprendido en la unidad:

| Práctica | Cómo | Apartado |
| --- | --- | --- |
| **Usuario propio sin privilegios** | `useradd -r -s /usr/sbin/nologin miapp` | 1.3 |
| **Permisos mínimos** | El código, de solo lectura para el usuario de la aplicación; solo los directorios de datos y registros, con escritura. | 5 |
| **Secretos protegidos** | Contraseñas y claves en un fichero `640` (propietario root, grupo de la aplicación) o en variables de entorno del servicio, nunca dentro del código. | 5 |
| **Gestionada como servicio** | Unidad de systemd con `User=`, `Restart=on-failure` y `enable`. | 8.3 |
| **Puertos no privilegiados** | En Linux, solo root puede abrir puertos por debajo del 1024. La aplicación escucha en un puerto alto (8080) y, si hace falta, un servidor web (Unidad 6) la publica en el 80/443. | 9.3 |
| **Registros controlados** | Mensajes al *journal* o a un fichero con rotación. | 10 |
| **Mantenimiento** | Actualizaciones automáticas de seguridad y vigilancia del espacio en disco. | 11 |
| **Permisos de despliegue limitados** | El equipo de desarrollo puede reiniciar el servicio con `sudo`, pero no tiene acceso completo de root. | 1.6 |

## 12.4 Caso práctico integrador

Una pequeña empresa de desarrollo te encarga preparar un **servidor Linux** para el equipo del proyecto *Agenda*, formado por las desarrolladoras `ana` y `luis`, y la jefa de proyecto `marta`. Requisitos:

1. Grupos `agenda` (ana, luis y marta) y `jefes` (marta).
2. Contraseñas de al menos 12 caracteres; las cuentas de ana y luis caducan el 30 de junio de 2027.
3. Directorio `/srv/agenda` donde todo el grupo pueda crear y modificar ficheros, que pertenezcan siempre al grupo `agenda`, y donde nadie pueda borrar lo de otro. Los demás usuarios del servidor no deben poder entrar.
4. Directorio `/srv/agenda/informes` donde solo `marta` pueda escribir, pero todo el grupo pueda leer.
5. La aplicación (de momento, un servidor web de prueba en Python en el puerto 8080) debe ejecutarse como servicio con el usuario `agenda-app`, arrancar sola y reiniciarse si falla.
6. Los miembros de `agenda` pueden **reiniciar** el servicio, pero no tienen más privilegios.
7. Comprobaciones: el servicio responde, sus registros se pueden consultar y se sabe qué puertos tiene abiertos el servidor.

{{% details "Ver solución" %}}
**1. Grupos y usuarios**

```bash
sudo groupadd agenda
sudo groupadd jefes
for u in ana luis marta; do
    sudo useradd -m -s /bin/bash -G agenda "$u"
done
sudo usermod -aG jefes marta
id marta                      # ... grupos=...(marta),...(agenda),...(jefes)
```

**2. Contraseñas y caducidad**

```bash
sudo apt install libpam-pwquality
sudo sed -i 's/^# *minlen.*/minlen = 12/' /etc/security/pwquality.conf
for u in ana luis marta; do sudo passwd "$u"; done     # Debe rechazar contraseñas cortas
sudo chage -E 2027-06-30 ana
sudo chage -E 2027-06-30 luis
sudo chage -l ana | grep -i "account expires"
```

**3. Directorio del proyecto**

```bash
sudo mkdir -p /srv/agenda
sudo chown root:agenda /srv/agenda
sudo chmod 3770 /srv/agenda                        # SGID + sticky, rwx para el grupo, nada para el resto
sudo setfacl -d -m g:agenda:rwX /srv/agenda        # Lo nuevo será modificable por el grupo
ls -ld /srv/agenda                                 # drwxrws--T+ root agenda
```

**4. Directorio de informes**

```bash
sudo mkdir /srv/agenda/informes
sudo chown marta:agenda /srv/agenda/informes
sudo setfacl -b -k /srv/agenda/informes                   # Quita las ACL heredadas de /srv/agenda
sudo chmod 2750 /srv/agenda/informes                      # marta rwx, grupo agenda r-x, resto nada
sudo setfacl -d -m u::rwx,g::rx,o::--- /srv/agenda/informes # Lo nuevo: el grupo solo podrá leer
getfacl /srv/agenda/informes
```

Al crearse dentro de `/srv/agenda`, el directorio `informes` **hereda** su ACL por defecto, que da `rwx` al grupo. Por eso primero se eliminan con `setfacl -b` (entradas de acceso) y `-k` (ACL por defecto), después se fijan los permisos con `chmod` y, por último, se define una ACL por defecto propia para que los ficheros que cree `marta` sean de solo lectura para el grupo, independientemente de su `umask`.

**5. Servicio de la aplicación**

```bash
sudo useradd -r -s /usr/sbin/nologin -d /opt/agenda agenda-app
sudo mkdir -p /opt/agenda
echo "<h1>Agenda funcionando</h1>" | sudo tee /opt/agenda/index.html > /dev/null
sudo chown -R root:agenda-app /opt/agenda
sudo chmod -R 750 /opt/agenda                      # La aplicación lee, pero no puede modificar su código

sudo tee /etc/systemd/system/agenda.service > /dev/null <<'EOF'
[Unit]
Description=Aplicación Agenda
After=network-online.target
Wants=network-online.target

[Service]
User=agenda-app
Group=agenda-app
WorkingDirectory=/opt/agenda
ExecStart=/usr/bin/python3 -m http.server 8080
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now agenda
```

**6. Reinicio delegado con `sudo`**

```bash
sudo visudo -f /etc/sudoers.d/agenda
```

```text
%agenda ALL=(root) /usr/bin/systemctl restart agenda.service
```

```bash
sudo -l -U ana                         # Muestra lo que ana puede ejecutar con sudo
```

**7. Comprobaciones**

```bash
systemctl status agenda                # active (running), usuario agenda-app
curl -s http://localhost:8080          # <h1>Agenda funcionando</h1>
ps -o user,pid,cmd -C python3          # Se ejecuta como agenda-app, no como root
sudo kill -9 "$(systemctl show -p MainPID --value agenda)"   # Simular un fallo…
sleep 6; systemctl is-active agenda    # …systemd lo ha reiniciado: active
journalctl -u agenda -n 20             # Registros del servicio
sudo ss -tlpn                          # Puertos en escucha: aparece 8080 con python3
```

Verifica también los permisos con distintos usuarios: `sudo -u luis touch /srv/agenda/prueba` (debe funcionar), `sudo -u luis touch /srv/agenda/informes/x` (debe fallar) y `sudo -u luis rm /srv/agenda/<fichero de ana>` (debe fallar por el *sticky bit*).
{{% /details %}}

> [!TIP]
> Como ampliación, realiza el **mismo caso en Windows**: grupos con `New-LocalGroup`, directivas con `net accounts`, carpeta con `icacls`, y para la aplicación un servicio o una tarea programada que se ejecute al iniciar el sistema con una cuenta sin privilegios.

## 12.5 Resumen de comandos de administración

| Tarea | Bash (Linux) | CMD (Windows) | PowerShell (Windows) |
| --- | --- | --- | --- |
| Usuario actual y sus grupos | `id` | `whoami /groups` | `whoami /groups` |
| Listar usuarios | `getent passwd` | `net user` | `Get-LocalUser` |
| Crear usuario | `useradd -m -s /bin/bash u` | `net user u * /add` | `New-LocalUser u` |
| Cambiar contraseña | `passwd u` | `net user u *` | `Set-LocalUser u -Password ...` |
| Deshabilitar cuenta | `usermod -L -e 1 u` | `net user u /active:no` | `Disable-LocalUser u` |
| Eliminar usuario | `userdel -r u` | `net user u /delete` | `Remove-LocalUser u` |
| Crear grupo | `groupadd g` | `net localgroup g /add` | `New-LocalGroup g` |
| Añadir a grupo | `usermod -aG g u` | `net localgroup g u /add` | `Add-LocalGroupMember g -Member u` |
| Directivas de contraseña | `chage`, `pwquality.conf` | `net accounts` | `secedit` |
| Ver permisos | `ls -l`, `getfacl` | `icacls f` | `Get-Acl f` |
| Cambiar permisos | `chmod`, `setfacl` | `icacls f /grant ...` | `Set-Acl` |
| Cambiar propietario | `chown u f` | `icacls f /setowner u` | `Set-Acl` (con `SetOwner`) |
| Compartir carpeta | `smb.conf` + `smbpasswd` | `net share` | `New-SmbShare` |
| Conectar recurso de red | `mount -t cifs` | `net use Z: \\srv\r` | `New-SmbMapping` |
| Listar procesos | `ps aux` | `tasklist` | `Get-Process` |
| Terminar proceso | `kill PID` | `taskkill /pid PID` | `Stop-Process -Id PID` |
| Estado de un servicio | `systemctl status s` | `sc query s` | `Get-Service s` |
| Arrancar / detener servicio | `systemctl start` / `stop s` | `net start` / `net stop s` | `Start-Service` / `Stop-Service s` |
| Inicio automático | `systemctl enable s` | `sc config s start= auto` | `Set-Service s -StartupType Automatic` |
| Memoria | `free -h` | `systeminfo` | `Get-CimInstance Win32_OperatingSystem` |
| Espacio en disco | `df -h` | `fsutil volume diskfree C:` | `Get-Volume` |
| Puertos en escucha | `ss -tulpn` | `netstat -ano` | `Get-NetTCPConnection -State Listen` |
| Registros | `journalctl` | `wevtutil qe System` | `Get-WinEvent` |
| Actualizar el sistema | `apt update && apt upgrade` | — | `winget upgrade --all` |
