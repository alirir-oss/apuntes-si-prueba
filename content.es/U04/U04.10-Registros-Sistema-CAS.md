# 10. Registros del sistema

Los **registros** (*logs*) son ficheros o bases de datos donde el sistema operativo, los servicios y las aplicaciones anotan, por orden cronológico, todo lo que ocurre: arranques y apagados, inicios de sesión, errores de los programas, instalación de paquetes, conexiones rechazadas… Cuando algo falla, los registros son **la primera fuente de información** para averiguar qué ha pasado.

Como desarrolladores, también escribiréis registros desde vuestras aplicaciones. Conocer cómo funcionan los del sistema os ayudará a hacerlo bien.

## 10.1 Niveles de gravedad

Cada mensaje de registro lleva un **nivel de gravedad**. El estándar *syslog*, usado en Linux, define ocho:

| Nivel | Nombre | Significado | Equivalente en Windows |
| --- | --- | --- | --- |
| 0 | `emerg` | El sistema no se puede usar. | Crítico |
| 1 | `alert` | Hay que actuar inmediatamente. | Crítico |
| 2 | `crit` | Condición crítica. | Crítico |
| 3 | `err` | Error. | Error |
| 4 | `warning` | Advertencia. | Advertencia |
| 5 | `notice` | Situación normal pero significativa. | Información |
| 6 | `info` | Mensaje informativo. | Información |
| 7 | `debug` | Información de depuración. | Detallado |

Los mismos niveles se usan en las bibliotecas de registro de los lenguajes de programación (por ejemplo, `logging` en Python o SLF4J en Java).

## 10.2 Linux: dos sistemas de registro

En las distribuciones actuales conviven dos sistemas:

| Sistema | Formato | Dónde guarda | Cómo se consulta |
| --- | --- | --- | --- |
| **systemd-journald** (el *journal*) | Binario, estructurado (cada mensaje lleva campos: servicio, PID, usuario, prioridad…) | `/var/log/journal/` (o en memoria, en `/run/log/journal/`, si no es persistente) | `journalctl` |
| **rsyslog** | Texto plano | Ficheros en `/var/log/` | `less`, `tail`, `grep` |

El *journal* recoge **todos** los mensajes y, si rsyslog está instalado, se los reenvía para que los escriba también en los ficheros de texto.

> [!NOTE]
> Algunas distribuciones ya no instalan rsyslog por defecto (por ejemplo, Debian desde la versión 12). En ellas no existen ficheros como `/var/log/syslog` o `/var/log/auth.log` y toda la información se consulta con `journalctl`. Compruébalo en tu sistema con `systemctl status rsyslog`. Si necesitas los ficheros de texto, se instala con `sudo apt install rsyslog`.

### Ficheros de `/var/log`

| Fichero | Contenido |
| --- | --- |
| `/var/log/syslog` | Mensajes generales del sistema (en Fedora/RHEL: `/var/log/messages`). |
| `/var/log/auth.log` | **Autenticación**: inicios de sesión, uso de `sudo`, conexiones SSH (en Fedora/RHEL: `/var/log/secure`). |
| `/var/log/kern.log` | Mensajes del núcleo. |
| `/var/log/dpkg.log` | Paquetes instalados, actualizados y eliminados. |
| `/var/log/apt/history.log` | Historial de órdenes `apt` (qué se instaló, cuándo y quién). |
| `/var/log/boot.log` | Mensajes del arranque. |
| `/var/log/wtmp`, `/var/log/btmp` | Inicios de sesión correctos y fallidos. Son binarios: se leen con `last` y `lastb` (apartado 1.7). |
| `/var/log/apache2/`, `/var/log/samba/`… | Registros propios de cada servicio. |

```bash
sudo tail -n 20 /var/log/auth.log             # Últimos 20 mensajes de autenticación
sudo tail -f /var/log/syslog                  # Seguir en tiempo real (Ctrl+C para salir)
sudo grep -i "failed password" /var/log/auth.log    # Intentos de acceso SSH fallidos
zgrep "install " /var/log/dpkg.log*           # Busca también en los ficheros antiguos comprimidos (.gz)
```

Para leer los registros sin `sudo`, el usuario debe pertenecer al grupo **`adm`** (ficheros de `/var/log`) o **`systemd-journal`** (*journal* completo). En Ubuntu, el primer usuario ya pertenece a `adm`.

### `journalctl`

| Opción | Función |
| --- | --- |
| (sin opciones) | Todo el *journal*, del más antiguo al más reciente, en un paginador. |
| `-r` | En orden inverso (lo más reciente primero). |
| `-n 50` | Solo los 50 últimos mensajes. |
| `-f` | Seguir en tiempo real. |
| `-b` | Solo desde el último arranque. `-b -1`: el arranque anterior. |
| `--list-boots` | Lista de arranques registrados. |
| `-u servicio` | Mensajes de una unidad de systemd. |
| `-p err` | Solo los de prioridad `err` o más grave. Se admite un rango: `-p warning..err`. |
| `-k` | Solo los mensajes del núcleo (equivale a `dmesg`). |
| `-t etiqueta` | Por identificador (por ejemplo, los mensajes enviados con `logger -t`). |
| `--since` / `--until` | Intervalo de tiempo: `"2026-11-08 09:00"`, `"1 hour ago"`, `today`, `yesterday`. |
| `_UID=1001` | Mensajes de los procesos de un usuario (filtro por campo). |
| `-o verbose` / `-o json-pretty` | Muestra todos los campos de cada mensaje. |
| `--no-pager` | Sin paginador (para usar en scripts y tuberías). |

```bash
journalctl -b -p err                        # Errores desde el último arranque
journalctl -u ssh --since today             # Mensajes de SSH de hoy
journalctl -u miapp -f                      # Seguir el registro de tu aplicación (apartado 8.3)
journalctl --since "1 hour ago" -p warning  # Advertencias y errores de la última hora
journalctl _COMM=sudo --since yesterday     # Uso de sudo desde ayer (_COMM: nombre del programa)
journalctl -k -b -1                         # Mensajes del núcleo del arranque anterior (por si se colgó)
```

### Gestión del espacio del *journal*

```bash
journalctl --disk-usage                     # Espacio que ocupa
sudo journalctl --vacuum-time=4weeks        # Borra los mensajes de hace más de 4 semanas
sudo journalctl --vacuum-size=500M          # Reduce el journal a 500 MB como máximo
```

El tamaño máximo permanente se configura con `SystemMaxUse=` en `/etc/systemd/journald.conf`. Para que el *journal* se guarde en el disco y no se pierda al reiniciar, debe existir el directorio `/var/log/journal` (en Ubuntu existe por defecto).

### Mensajes del núcleo: `dmesg`

```bash
sudo dmesg -T | tail -n 20       # -T: fechas legibles
sudo dmesg -T --level=err,warn   # Solo errores y advertencias
sudo dmesg -w                    # Seguir en tiempo real (útil al conectar un dispositivo USB)
```

### Escribir en el registro: `logger`

Tus scripts pueden enviar mensajes al registro del sistema, que luego se consultan con las mismas herramientas:

```bash
logger "Copia de seguridad terminada"
logger -t backup -p user.err "No queda espacio en el destino"
journalctl -t backup
```

### Rotación de registros: `logrotate`

Si los registros crecieran indefinidamente, acabarían llenando el disco. **`logrotate`** se ejecuta a diario (mediante un *timer* de systemd) y, según su configuración, **rota** los ficheros: renombra el actual (`syslog` → `syslog.1`), comprime los antiguos (`syslog.2.gz`…), borra los que superan el número máximo y empieza un fichero nuevo.

La configuración general está en `/etc/logrotate.conf` y la de cada servicio en `/etc/logrotate.d/`. Ejemplo para los registros de tu aplicación:

```text
# /etc/logrotate.d/miapp
/var/log/miapp/*.log {
    # Rotar cada semana (también: daily, monthly)
    weekly
    # Conservar 8 ficheros antiguos
    rotate 8
    # Comprimir los antiguos con gzip…
    compress
    # …excepto el más reciente (por si la aplicación aún escribe en él)
    delaycompress
    # No dar error si no existe el fichero ni rotarlo si está vacío
    missingok
    notifempty
    # Permisos, propietario y grupo del fichero nuevo
    create 0640 miapp adm
}
```

> [!WARNING]
> En los ficheros de `logrotate` los comentarios deben ir en **líneas propias** que empiecen por `#`. Un comentario al final de una directiva (`weekly # cada semana`) provoca un error.

```bash
sudo logrotate -d /etc/logrotate.d/miapp     # Simulación (debug): muestra qué haría sin hacerlo
sudo logrotate -f /etc/logrotate.d/miapp     # Fuerza una rotación ahora
```

## 10.3 Windows: el Visor de eventos

En Windows, los registros se llaman **registros de eventos** y se consultan con el **Visor de eventos** (`eventvwr.msc`).

### Registros principales

| Registro | Contenido |
| --- | --- |
| **Aplicación** | Eventos de los programas (errores de aplicaciones, mensajes de instaladores…). |
| **Seguridad** | Eventos de **auditoría**: inicios de sesión, cambios en cuentas, accesos a ficheros auditados. Solo los administradores pueden leerlo. |
| **Instalación** | Instalación de actualizaciones y características de Windows. |
| **Sistema** | Eventos de los componentes de Windows: servicios, controladores, arranque y apagado. |
| **Registros de aplicaciones y servicios** | Registros específicos de cada componente (PowerShell, Windows Defender, Programador de tareas…). |

### Información de un evento

| Campo | Descripción |
| --- | --- |
| **Nivel** | Crítico, Error, Advertencia, Información, Detallado. En el registro *Seguridad*: Auditoría correcta o Auditoría errónea. |
| **Fecha y hora** | Cuándo ocurrió. |
| **Origen** | Componente o programa que lo generó. |
| **Id. del evento** | Número que identifica el **tipo** de evento. Junto con el origen, permite buscar información sobre él. |
| **Usuario** | Cuenta relacionada con el evento. |
| **Descripción** | Texto explicativo (pestaña *General*) y datos completos en XML (pestaña *Detalles*). |

### Identificadores de evento importantes

| Registro | Id. | Significado |
| --- | --- | --- |
| Seguridad | **4624** | Inicio de sesión correcto. |
| Seguridad | **4625** | Inicio de sesión **fallido**. |
| Seguridad | **4634** / **4647** | Cierre de sesión. |
| Seguridad | **4720** | Se ha creado una cuenta de usuario. |
| Seguridad | **4726** | Se ha eliminado una cuenta de usuario. |
| Seguridad | **4732** | Se ha añadido un miembro a un grupo local. |
| Seguridad | **4740** | Una cuenta se ha **bloqueado** (apartado 4). |
| Sistema | **6005** / **6006** | El servicio de registro de eventos se ha iniciado / detenido (indica arranque / apagado). |
| Sistema | **1074** | Un usuario o un proceso ha iniciado el apagado o reinicio. |
| Sistema | **41** (origen *Kernel-Power*) | El sistema se reinició sin apagarse correctamente (corte de luz, cuelgue). |
| Sistema | **7036** | Un servicio ha cambiado de estado (iniciado, detenido). |

> [!NOTE]
> Los eventos del registro *Seguridad* dependen de la **directiva de auditoría**: solo se registra lo que está configurado para auditarse. Los inicios de sesión y la gestión de cuentas se auditan por defecto en Windows 11, pero otros eventos, como los accesos a ficheros, hay que activarlos (en `secpol.msc` > *Directivas locales > Directiva de auditoría*, o con `auditpol`). Puedes ver la configuración actual con `auditpol /get /category:*` en una consola de administrador.

### Trabajar con el Visor de eventos

- **Filtrar registro actual** (panel derecho): mostrar solo ciertos niveles, orígenes, identificadores o un intervalo de tiempo.
- **Crear vista personalizada**: guardar un filtro, incluso combinando varios registros. La vista predefinida *Eventos administrativos* reúne los errores y advertencias de todos los registros.
- **Adjuntar tarea a este evento**: ejecutar un programa o script automáticamente cuando se produzca un evento concreto (crea una tarea en el Programador de tareas).
- **Guardar todos los eventos como…**: exportar el registro a un fichero `.evtx` para analizarlo en otro equipo.
- **Propiedades del registro**: tamaño máximo y qué hacer cuando se llena (sobrescribir los eventos antiguos, archivar…). Es el equivalente a la rotación de Linux.

## 10.4 Windows: registros desde la línea de comandos

### PowerShell: `Get-WinEvent`

```powershell
Get-WinEvent -ListLog * | Where-Object RecordCount -gt 0 |
    Sort-Object RecordCount -Descending | Select-Object -First 10 LogName, RecordCount

Get-WinEvent -LogName System -MaxEvents 20            # Los 20 eventos más recientes de Sistema

# -FilterHashtable filtra en el propio servicio de registro, mucho más rápido que Where-Object
Get-WinEvent -FilterHashtable @{
    LogName   = 'System'
    Level     = 2                                     # 1 Crítico, 2 Error, 3 Advertencia, 4 Información
    StartTime = (Get-Date).AddDays(-1)                # Últimas 24 horas
}

# Inicios de sesión fallidos de la última semana (como administrador)
Get-WinEvent -FilterHashtable @{ LogName = 'Security'; Id = 4625; StartTime = (Get-Date).AddDays(-7) } |
    Select-Object TimeCreated, Id, Message | Format-List
```

> [!NOTE]
> El antiguo *cmdlet* `Get-EventLog` solo existe en Windows PowerShell 5.1 y **no está disponible en PowerShell 7**. Utiliza siempre `Get-WinEvent`.

### CMD: `wevtutil` y `eventcreate`

```bat
wevtutil el                                  :: Lista todos los registros
wevtutil qe System /c:5 /rd:true /f:text     :: Los 5 eventos más recientes de Sistema, en texto
wevtutil epl System C:\Temp\sistema.evtx     :: Exporta el registro a un fichero
wevtutil gl Application                      :: Configuración del registro (tamaño máximo…)

:: Escribir un evento propio en el registro Aplicación (equivale a logger en Linux)
eventcreate /T WARNING /ID 100 /L APPLICATION /SO MiScript /D "No queda espacio en el destino"
```

## 10.5 Comparativa

| Tarea | Linux | Windows |
| --- | --- | --- |
| Herramienta principal | `journalctl`, ficheros de `/var/log` | Visor de eventos (`eventvwr.msc`), `Get-WinEvent` |
| Mensajes generales | `/var/log/syslog`, `journalctl` | Registro *Sistema* |
| Autenticación | `/var/log/auth.log`, `journalctl _COMM=sshd` | Registro *Seguridad* (4624, 4625…) |
| Desde el último arranque | `journalctl -b` | Filtrar desde el evento 6005 |
| Solo errores | `journalctl -p err` | Filtro por nivel *Error*, `Level = 2` |
| Seguir en tiempo real | `journalctl -f`, `tail -f` | (Vista actualizada manualmente o `Get-WinEvent` en bucle) |
| Escribir un mensaje propio | `logger` | `eventcreate`, `Write-EventLog` (solo PowerShell 5.1) |
| Limitar el tamaño | `logrotate`, `journald.conf` | Propiedades del registro |

## Ejercicios resueltos

### Ejercicio 10.1. Investigar un acceso con `sudo`

Averigua quién ha usado `sudo` hoy en tu Linux y qué órdenes ha ejecutado.

{{% details "Ver solución" %}}
```bash
journalctl _COMM=sudo --since today --no-pager
# nov 08 10:15:02 equipo sudo[4120]:   alumno : TTY=pts/0 ; PWD=/home/alumno ; USER=root ; COMMAND=/usr/bin/apt update
```

Si rsyslog está instalado, también: `sudo grep sudo /var/log/auth.log`. Cada línea indica el usuario, la terminal, el directorio, el usuario de destino y la orden ejecutada. Por eso `sudo` es preferible a compartir la contraseña de root: queda constancia de quién hizo qué.
{{% /details %}}

### Ejercicio 10.2. Detectar un ataque de fuerza bruta por SSH

Desde otra máquina, intenta conectarte varias veces por SSH a tu servidor con una contraseña incorrecta. Después, en el servidor, cuenta los intentos fallidos y obtén las direcciones IP de origen.

{{% details "Ver solución" %}}
```bash
# Desde el cliente (varias veces, con contraseña errónea)
ssh usuario_inexistente@IP-SERVIDOR

# En el servidor
journalctl -u ssh --since today | grep -i "failed password\|invalid user"
journalctl -u ssh --since today --no-pager |
    grep -oE 'from [0-9.]+' | sort | uniq -c | sort -rn
#      6 from 192.168.1.35
```

`grep -o` muestra solo la parte que coincide con el patrón; `sort | uniq -c` cuenta las repeticiones y `sort -rn` las ordena de mayor a menor (Unidad 3). En un servidor expuesto a Internet verás cientos de intentos al día: por eso se recomienda desactivar el acceso por contraseña en SSH y usar claves (Unidad 6), además de herramientas como *fail2ban*.
{{% /details %}}

### Ejercicio 10.3. Inicios de sesión fallidos en Windows

Provoca dos inicios de sesión fallidos con una cuenta de prueba en Windows. Después, con PowerShell, obtén la fecha, el nombre de la cuenta y el motivo de los eventos 4625 de la última hora.

{{% details "Ver solución" %}}
```powershell
# Ejecutar como administrador
Get-WinEvent -FilterHashtable @{ LogName = 'Security'; Id = 4625; StartTime = (Get-Date).AddHours(-1) } |
    ForEach-Object {
        $xml = [xml]$_.ToXml()                       # Convierte el evento a XML para leer sus campos
        $datos = @{}
        foreach ($d in $xml.Event.EventData.Data) { $datos[$d.Name] = $d.'#text' }
        [PSCustomObject]@{
            Fecha   = $_.TimeCreated
            Cuenta  = $datos['TargetUserName']
            Estado  = $datos['SubStatus']            # 0xC000006A = contraseña incorrecta
            Origen  = $datos['IpAddress']
        }
    } | Format-Table -AutoSize
```

El código `SubStatus` indica el motivo: `0xC000006A` contraseña incorrecta, `0xC0000064` el usuario no existe, `0xC0000234` cuenta bloqueada. Convertir el evento a XML es la forma fiable de obtener sus campos, porque el texto del mensaje (`Message`) depende del idioma.
{{% /details %}}

### Ejercicio 10.4. Rotación para una aplicación propia

Tu aplicación escribe en `/var/log/miapp/app.log`. Configura `logrotate` para rotarlo a diario, conservar 14 días comprimidos y crear el fichero nuevo con propietario `miapp`. Comprueba la configuración sin aplicarla.

{{% details "Ver solución" %}}
```bash
sudo mkdir -p /var/log/miapp
sudo chown miapp:adm /var/log/miapp
sudo tee /etc/logrotate.d/miapp > /dev/null <<'EOF'
/var/log/miapp/app.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    create 0640 miapp adm
}
EOF
sudo logrotate -d /etc/logrotate.d/miapp
```

La salida de `-d` muestra qué ficheros se considerarían y qué acciones se harían, sin modificar nada. 
{{% /details %}}
