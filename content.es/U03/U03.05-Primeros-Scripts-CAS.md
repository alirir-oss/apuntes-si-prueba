# 5. Primeros scripts

## 5.1 ¿Qué es un script?

Un **script** es un fichero de **texto plano** que contiene una secuencia de órdenes que la shell ejecuta una detrás de otra. Todo lo que se puede escribir en la terminal se puede poner en un script, y además Bash ofrece elementos propios de un lenguaje de programación: variables, condiciones, bucles y funciones.

¿Para qué sirven? Para **automatizar** tareas repetitivas o propensas a errores: preparar un entorno de desarrollo, hacer copias de seguridad, desplegar una aplicación, procesar ficheros de registro, dar de alta usuarios…

| | Programa compilado (Java, C…) | Script de Bash |
| --- | --- | --- |
| Ejecución | Se traduce antes (compilación) a código máquina o *bytecode*. | Un **intérprete** (`bash`) lee y ejecuta las líneas una a una. |
| Errores | Muchos se detectan al compilar. | Se detectan al llegar a la línea con el error, en tiempo de ejecución. |
| Punto fuerte | Rendimiento, programas grandes. | "Pegar" programas existentes y automatizar el sistema. |

> [!NOTE]
> Bash es ideal para scripts de unas decenas o pocos cientos de líneas que combinan órdenes del sistema. Si el problema requiere estructuras de datos complejas o mucho cálculo, es mejor un lenguaje de propósito general como Python.

## 5.2 Nuestro primer script

{{% steps %}}
1. ## Crear el fichero

   Usa cualquier editor de texto plano: `nano`, `vim` o VS Code. Por convenio, los scripts de shell llevan la extensión `.sh` (Linux no la necesita, pero ayuda a identificarlos).

   ```bash
   mkdir -p ~/scripts && cd ~/scripts
   nano hola.sh
   ```

2. ## Escribir el contenido

   ```bash
   #!/bin/bash
   # hola.sh - Mi primer script
   # Muestra un saludo y algunos datos del sistema

   echo "¡Hola, $USER!"
   echo "Hoy es $(date +%d/%m/%Y) y estás en el equipo $(hostname)."
   echo "Tu directorio actual es: $(pwd)"
   ```

   En `nano` se guarda con `Ctrl+O` y se sale con `Ctrl+X`.

3. ## Dar permiso de ejecución

   ```bash
   chmod u+x hola.sh     # o chmod 755 hola.sh
   ```

4. ## Ejecutarlo

   ```bash
   ./hola.sh
   ```

   ```text
   ¡Hola, alumno!
   Hoy es 08/11/2026 y estás en el equipo dam-pc.
   Tu directorio actual es: /home/alumno/scripts
   ```
{{% /steps %}}

### La primera línea: el *shebang*

La línea `#!/bin/bash` se llama ***shebang*** (por los caracteres `#` *sharp* y `!` *bang*). Debe ser **la primera línea** del fichero, sin espacios delante, e indica al sistema qué intérprete debe ejecutar el script.

| *Shebang* | Uso |
| --- | --- |
| `#!/bin/bash` | Ejecutar con Bash. Es el que usaremos en esta unidad. |
| `#!/usr/bin/env bash` | Busca `bash` en el `PATH`. Más portable (por ejemplo, en macOS con Bash instalado aparte). |
| `#!/bin/sh` | Shell POSIX mínima (en Debian/Ubuntu es `dash`). **No** admite muchas características de Bash como `[[ ]]` o los *arrays*. |
| `#!/usr/bin/env python3` | El mismo mecanismo sirve para otros lenguajes interpretados. |

### Comentarios

Todo lo que sigue a una `#` (excepto el *shebang*) es un **comentario** y Bash lo ignora. Úsalos para explicar **por qué** se hace algo, no para repetir lo que ya dice el código.

```bash
# Comentario de línea completa
echo "Hola"   # Comentario al final de una línea
```

## 5.3 Formas de ejecutar un script

| Forma | ¿Necesita `chmod +x`? | ¿Usa el *shebang*? | Dónde se ejecuta |
| --- | --- | --- | --- |
| `./hola.sh` | Sí | Sí | En una **nueva** shell (subproceso). |
| `bash hola.sh` | No | No (se fuerza Bash) | En una nueva shell. |
| `hola.sh` (sin ruta) | Sí | Sí | Solo funciona si el directorio está en el `PATH`. |
| `source hola.sh` o `. hola.sh` | No | No | En la **shell actual**: las variables y los cambios de directorio permanecen al terminar. |

¿Por qué hay que escribir `./` delante? Porque, por seguridad, la shell solo busca las órdenes en los directorios de la variable `PATH`, y el directorio actual no está incluido. `./` indica explícitamente "el fichero `hola.sh` de este directorio".

Para poder ejecutar tus scripts desde cualquier lugar, guárdalos en `~/.local/bin`, un directorio que las distribuciones actuales añaden al `PATH` automáticamente si existe:

```bash
mkdir -p ~/.local/bin
cp hola.sh ~/.local/bin/hola     # Se puede quitar la extensión
# Si no estaba, cierra y abre la terminal (o ejecuta: source ~/.profile)
hola                             # ¡Ya funciona como cualquier otro comando!
echo "$PATH"                     # Directorios donde se buscan las órdenes
```

> [!WARNING]
> **Scripts creados en Windows.** Windows termina las líneas con dos caracteres (`\r\n`, CRLF) y Linux con uno (`\n`, LF). Un script con finales CRLF falla con errores extraños como `/bin/bash^M: bad interpreter` o `$'\r': command not found`. Solución: en VS Code, haz clic en `CRLF` en la barra de estado y cámbialo a `LF`; o corrige el fichero con `sed -i 's/\r$//' script.sh` (o `dos2unix script.sh`).

## 5.4 Código de salida: `exit`

Toda orden, al terminar, devuelve al sistema un número entre 0 y 255 llamado **código de salida** (*exit status*):

- `0` significa **éxito**.
- Cualquier otro valor indica **error** (cada programa documenta el significado de sus códigos).

El código de la última orden se guarda en la variable especial `$?`. En nuestros scripts lo fijamos con `exit`:

```bash
ls /etc > /dev/null
echo $?          # 0  -> correcto
ls /noexiste
echo $?          # 2  -> error (ls usa 2 para "problema grave")
```

```bash
#!/bin/bash
# comprobar_red.sh - Termina con 0 si hay conexión a Internet y con 1 si no
if ping -c 1 -W 2 8.8.8.8 > /dev/null 2>&1; then
    echo "Conexión correcta"
    exit 0
else
    echo "Sin conexión" >&2     # >&2 envía el mensaje a la salida de errores
    exit 1
fi
```

Si un script no ejecuta `exit`, su código de salida es el de la última orden ejecutada. Un buen script devuelve siempre un código que refleje si ha cumplido su tarea, para que otros scripts (o herramientas como `cron` o un *pipeline* de CI) puedan saberlo.

## 5.5 Depurar scripts

Cuando un script no hace lo que esperamos, tenemos varias herramientas:

| Herramienta | Uso |
| --- | --- |
| `bash -n script.sh` | Comprueba la **sintaxis** sin ejecutar nada. |
| `bash -x script.sh` | Ejecuta mostrando cada orden (precedida de `+`) **después** de sustituir variables. Es la herramienta de depuración más útil. |
| `set -x` … `set +x` | Activa y desactiva la traza solo en una parte del script. |
| `echo "DEBUG: var=$var" >&2` | Mensajes de depuración por la salida de errores. |
| **ShellCheck** | Analizador que detecta errores típicos y malas prácticas. Instálalo con `sudo apt install shellcheck` o como extensión de VS Code. |

```bash
bash -x hola.sh
```

```text
+ echo '¡Hola, alumno!'
¡Hola, alumno!
++ date +%d/%m/%Y
++ hostname
+ echo 'Hoy es 08/11/2026 y estás en el equipo dam-pc.'
…
```

> [!TIP]
> Acostúmbrate a pasar **ShellCheck** a todos tus scripts (`shellcheck script.sh`). Cada aviso tiene un código (por ejemplo `SC2086`) que se puede buscar en <https://www.shellcheck.net/wiki/> con una explicación detallada.

## 5.6 Modo estricto

Por defecto, Bash es muy permisivo: si una orden falla, **sigue** con la siguiente; y si usamos una variable que no existe, la sustituye por una cadena vacía sin avisar. Esto puede provocar desastres. Muchos scripts profesionales empiezan con:

```bash
#!/bin/bash
set -euo pipefail
```

| Opción | Efecto |
| --- | --- |
| `-e` (*errexit*) | El script se detiene si una orden falla (devuelve un código distinto de 0). |
| `-u` (*nounset*) | Usar una variable no definida es un error. |
| `-o pipefail` | Una tubería falla si falla **cualquiera** de sus órdenes, no solo la última. |

```bash
#!/bin/bash
set -euo pipefail
DIR_TRABAJO="/tmp/mi_app"
cd "$DIR_TRABAJO"            # Si el directorio no existe, el script se detiene aquí…
rm -rf ./*                   # …y nunca llega a borrar el contenido del directorio equivocado
```

> [!NOTE]
> `set -e` tiene excepciones (no se aplica, por ejemplo, a las órdenes usadas como condición en un `if` o antes de `&&`/`||`). Es una red de seguridad, no un sustituto de comprobar los errores de las operaciones importantes.

## 5.7 Plantilla y buenas prácticas

Esta plantilla recoge las buenas prácticas que iremos aplicando en los siguientes apartados:

```bash
#!/bin/bash
#==============================================================
# Nombre:      nombre_script.sh
# Descripción: Qué hace el script, en una o dos líneas.
# Uso:         ./nombre_script.sh <argumento1> [argumento2]
# Autor:       Nombre Apellido
# Fecha:       2026-11-08
#==============================================================
set -euo pipefail

# --- Constantes y configuración -------------------------------
readonly LOG="/tmp/nombre_script.log"

# --- Funciones ------------------------------------------------
uso() {
    echo "Uso: $0 <argumento1> [argumento2]" >&2
    exit 1
}

# --- Programa principal --------------------------------------
[[ $# -ge 1 ]] || uso      # Comprobación de argumentos (apartados 6 y 7)

echo "Procesando $1…" | tee -a "$LOG"
exit 0
```

**Buenas prácticas:**

1. *Shebang* en la primera línea y cabecera que explique qué hace el script y cómo se usa.
2. Nombres de variables y funciones **descriptivos**.
3. Variables **siempre entre comillas dobles**: `"$fichero"` (lo veremos en el apartado 6).
4. Comprobar los argumentos y las condiciones previas (que existan los ficheros, que se tengan permisos…) antes de actuar.
5. Mensajes de error claros, enviados a la salida de errores (`>&2`), y códigos de salida coherentes.
6. Probar primero en un entorno seguro (un directorio de pruebas o un contenedor), sobre todo si el script borra o modifica ficheros.
7. Pasar **ShellCheck** y sangrar el código para que se lea con facilidad.

### Ejercicio 5.1. Ficha del sistema

Crea el script `ficha.sh` que muestre, con un título y una línea por dato: el usuario, el nombre del equipo, la distribución, la versión del *kernel*, el tiempo encendido y el espacio libre en `/`.

{{% details "Ver solución" %}}
```bash
#!/bin/bash
# ficha.sh - Muestra una ficha resumen del sistema

echo "===== FICHA DEL SISTEMA ====="
echo "Usuario:       $(whoami)"
echo "Equipo:        $(hostname)"
# /etc/os-release define la variable PRETTY_NAME; la cargamos con source en un subshell
echo "Distribución:  $(. /etc/os-release && echo "$PRETTY_NAME")"
echo "Kernel:        $(uname -r)"
echo "Encendido:     $(uptime -p)"
echo "Libre en /:    $(df -h / | awk 'NR == 2 { print $4 }')"
echo "============================="
```

```bash
chmod +x ficha.sh
./ficha.sh
```
{{% /details %}}

### Ejercicio 5.2. Encontrar el error

Este script debería mostrar la fecha, pero al ejecutarlo con `./fecha.sh` aparece `Permission denied`; después de solucionarlo, aparece `fecha: command not found`. Explica y corrige ambos errores.

```bash
#!/bin/bash
fecha = $(date +%F)
echo "Hoy es $fecha"
```

{{% details "Ver solución" %}}
1. **`Permission denied`**: el fichero no tiene permiso de ejecución. Se corrige con `chmod u+x fecha.sh`.
2. **`fecha: command not found`**: en Bash **no puede haber espacios** alrededor del `=` en una asignación. Con espacios, Bash interpreta `fecha` como una orden a la que se le pasan los argumentos `=` y `2026-11-08`.

```bash
#!/bin/bash
fecha=$(date +%F)
echo "Hoy es $fecha"
```

Con `bash -x fecha.sh` habríamos visto la línea `+ fecha = 2026-11-08`, que delata el problema. ShellCheck también lo detecta y propone la corrección.
{{% /details %}}

### Ejercicio 5.3. `./script` frente a `source script`

Crea `ir_tmp.sh` con el contenido siguiente y ejecútalo de las dos formas. ¿En qué directorio te encuentras después de cada una? ¿Por qué?

```bash
#!/bin/bash
cd /tmp
echo "Dentro del script estoy en: $(pwd)"
```

{{% details "Ver solución" %}}
```bash
chmod +x ir_tmp.sh
./ir_tmp.sh      # Dentro del script estoy en: /tmp
pwd              # /home/alumno/scripts -> ¡no hemos cambiado!
source ir_tmp.sh # Dentro del script estoy en: /tmp
pwd              # /tmp -> ahora sí
```

Con `./ir_tmp.sh` el script se ejecuta en un **proceso hijo**: el `cd` cambia el directorio de ese proceso, que desaparece al terminar. Con `source`, las órdenes se ejecutan en la **shell actual**, así que el cambio permanece. Por eso los ficheros de configuración como `~/.bashrc` se cargan con `source`.
{{% /details %}}
