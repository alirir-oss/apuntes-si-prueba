# 5. Permisos en Linux: UGO avançat i ACL

En la Unitat 3 (apartat 2.7) vas aprendre els permisos bàsics `rwx` i l'ordre `chmod`. Aquest model s'anomena **UGO** perquè distingix tres classes d'usuaris: el propietari (*User*), el grup (*Group*) i la resta (*Others*). En aquest apartat el completes amb:

- El canvi de **propietari** i de **grup** dels fitxers.
- La **màscara** que decidix els permisos dels fitxers nous.
- Els **permisos especials** SUID, SGID i *sticky bit*.
- Les **llistes de control d'accés** (ACL), que superen les limitacions del model UGO.

## 5.1 Repàs: com decidix Linux si tens permís

Quan un procés intenta accedir a un fitxer, el sistema comprova **en aquest ordre** i s'atura en la **primera** coincidència:

1. Si l'usuari és **root**, es permet l'accés (excepte executar un fitxer que no tinga cap permís `x`).
2. Si l'usuari és el **propietari**, s'apliquen els permisos d'`u`.
3. Si l'usuari pertany al **grup** del fitxer, s'apliquen els permisos de `g`.
4. En un altre cas, s'apliquen els permisos d'`o`.

> [!NOTE]
> Com que només s'aplica la primera coincidència, un propietari amb permisos `---` **no** pot llegir el seu fitxer encara que el grup o la resta sí que en tinguen permís. És poc habitual, però demostra que els permisos no se sumen.

Recorda també que, per a esborrar o reanomenar un fitxer, el que importa és el permís d'**escriptura en el directori** que el conté, no els permisos del fitxer mateix.

## 5.2 Canviar propietari i grup: `chown` i `chgrp`

| Ordre | Funció |
| --- | --- |
| `chown usuari fitxer` | Canvia el propietari. |
| `chown usuari:grup fitxer` | Canvia el propietari i el grup alhora. |
| `chown :grup fitxer` | Canvia només el grup. |
| `chgrp grup fitxer` | Canvia només el grup. |
| `-R` | Recursiu: aplica el canvi a un directori i a tot el seu contingut. |

```bash
sudo chown ana informe.txt              # El propietari passa a ser ana
sudo chown ana:dam1 informe.txt         # Propietari ana i grup dam1
sudo chown -R miapp:miapp /opt/miapp    # Tota l'aplicació pertany al seu usuari de servei
chgrp dam1 practica.sh                  # Un usuari pot canviar el grup a un dels SEUS grups
```

Només **root** pot canviar el propietari d'un fitxer. El propietari pot canviar el grup, però només a un dels grups als quals pertany.

## 5.3 Permisos per defecte: `umask`

Quan un programa crea un fitxer, sol·licita uns permisos inicials: normalment `666` (`rw-rw-rw-`) per als fitxers i `777` (`rwxrwxrwx`) per als directoris. La **màscara** (`umask`) indica quins permisos es **lleven** d'aquests valors inicials.

```text
Permisos finals = permisos inicials  SENSE  els bits que estiguen a 1 en la màscara
```

| `umask` | Fitxers (des de 666) | Directoris (des de 777) | Ús típic |
| --- | --- | --- | --- |
| `022` | `644` `rw-r--r--` | `755` `rwxr-xr-x` | root i servidors: tots poden llegir, només el propietari escriu. |
| `002` | `664` `rw-rw-r--` | `775` `rwxrwxr-x` | Treball en grup: el grup també pot escriure. |
| `027` | `640` `rw-r-----` | `750` `rwxr-x---` | La resta d'usuaris no pot ni llegir. |
| `077` | `600` `rw-------` | `700` `rwx------` | Màxima privacitat. |

> [!IMPORTANT]
> La màscara **no és una resta aritmètica**: indica quins bits s'eliminen. Amb `umask 033`, els fitxers queden amb `644` (no amb `633`), perquè a `rw-` no se li pot llevar una `x` que no tenia. A més, la màscara **mai no afig** permisos: un fitxer nou mai no tindrà permís d'execució per molt que canvies la màscara; se li dona després amb `chmod +x`.

```bash
umask              # Mostra la màscara actual en octal (0002)
umask -S           # La mostra en notació simbòlica (u=rwx,g=rwx,o=rx)
umask 027          # Canvia la màscara NOMÉS per a aquesta shell i els seus processos fills
touch prova && mkdir dir_prova && ls -ld prova dir_prova
# -rw-r----- ... prova
# drwxr-x--- ... dir_prova
```

Perquè la màscara siga permanent:

- **Per a un usuari**: afig `umask 027` al final de `~/.bashrc` o `~/.profile`.
- **Per a tots**: modifica la variable `UMASK` de `/etc/login.defs`, que aplica el mòdul PAM `pam_umask` en iniciar sessió.

> [!NOTE]
> En Ubuntu, la màscara habitual dels usuaris normals és `0002`, perquè cada usuari té el seu propi **grup privat** (amb el mateix nom) i ningú més no hi pertany. Per a root és `0022`.

## 5.4 Permisos especials

A més de `rwx`, cada fitxer té tres bits especials, que es representen amb un **quart dígit octal** a l'esquerra.

| Permís | Octal | Sobre un fitxer executable | Sobre un directori | Es veu en `ls -l` |
| --- | --- | --- | --- | --- |
| **SUID** (*Set User ID*) | `4` | El programa s'executa amb els permisos del seu **propietari**, no de qui el llança. | Sense efecte. | `s` en la `x` del propietari: `rwsr-xr-x` |
| **SGID** (*Set Group ID*) | `2` | El programa s'executa amb els permisos del seu **grup**. | Els fitxers que es creen dins **hereten el grup del directori**. | `s` en la `x` del grup: `rwxrwsr-x` |
| ***Sticky bit*** | `1` | Sense efecte en Linux. | Dins, cada usuari **només pot esborrar o reanomenar els seus propis fitxers**, encara que tinga permís d'escriptura en el directori. | `t` en la `x` de la resta: `rwxrwxrwt` |

Si el permís especial està actiu però la `x` corresponent no, la lletra apareix en **majúscula** (`S` o `T`), cosa que normalment indica un error de configuració.

### Exemples reals

```bash
ls -l /usr/bin/passwd
# -rwsr-xr-x 1 root root ... /usr/bin/passwd
```

`passwd` té **SUID** i el seu propietari és root. Per això un usuari normal pot canviar la seua contrasenya, encara que això implica escriure en `/etc/shadow`, un fitxer que només root pot modificar.

```bash
ls -ld /tmp
# drwxrwxrwt 20 root root ... /tmp
```

`/tmp` té permisos `777` perquè tots puguen crear fitxers temporals, i el ***sticky bit*** impedix que un usuari esborre els fitxers d'un altre.

### Assignar permisos especials

```bash
chmod u+s programa         # SUID           (octal: chmod 4755 programa)
chmod g+s directori        # SGID           (octal: chmod 2775 directori)
chmod +t directori         # Sticky bit     (octal: chmod 1777 directori)
chmod 3770 compartit       # SGID + sticky (2 + 1) i permisos rwxrwx---
```

> [!CAUTION]
> Un programa amb SUID de root és un **risc de seguretat**: si té una fallada, un atacant pot aprofitar-la per a aconseguir privilegis d'administrador. No poses mai SUID a scripts ni a programes que no ho necessiten. Revisar quins programes tenen SUID és una tasca habitual d'auditoria:
>
> ```bash
> sudo find / -xdev -perm -4000 -type f -ls 2>/dev/null
> ```

### Cas pràctic: directori de projecte compartit

Volem que els membres del grup `dam1` treballen junts en `/srv/projecte`: tots poden crear i modificar fitxers, ningú més no pot entrar, i ningú no pot esborrar els fitxers d'un altre.

```bash
sudo mkdir -p /srv/projecte
sudo chown root:dam1 /srv/projecte
sudo chmod 3770 /srv/projecte     # 2 = SGID (heretar grup) + 1 = sticky; rwx per a root i dam1
ls -ld /srv/projecte
# drwxrws--T 2 root dam1 ... /srv/projecte
```

- Gràcies al **SGID**, tot el que es cree dins pertanyerà al grup `dam1` (i no al grup privat de qui el crea).
- Gràcies al ***sticky bit***, cada usuari només pot esborrar els seus propis fitxers. Apareix com a `T` majúscula perquè la resta no té `x`, cosa que és correcta en aquest cas: el *sticky bit* només afecta els usuaris que poden escriure en el directori.
- Perquè els companys puguen **modificar** els fitxers, aquests han de tindre permís d'escriptura per al grup: els usuaris han d'utilitzar `umask 002` o, millor, s'utilitza una **ACL per defecte** (apartat 5.6).

## 5.5 Atributs estesos: `chattr` i `lsattr`

Els sistemes d'arxius ext4 (i altres) admeten **atributs** que s'apliquen fins i tot a root:

```bash
sudo chattr +i config.ini      # Immutable: ningú (ni root) no pot modificar-lo, esborrar-lo ni reanomenar-lo
lsattr config.ini              # ----i---------e------- config.ini
sudo chattr -i config.ini      # Lleva l'atribut
sudo chattr +a registre.log    # Només afegir (append): es pot escriure al final, però no esborrar contingut
```

## 5.6 Llistes de control d'accés (ACL)

### Per què fan falta

El model UGO només permet assignar permisos a **un** propietari i a **un** grup. Imagina que en `/srv/projecte` (grup `dam1`) la professora `marta` necessita **només llegir** i l'alumne `pablo`, d'un altre grup, necessita **llegir i escriure**. Amb UGO hauries de crear grups nous per a cada combinació. Les **ACL** (*Access Control Lists*) resolen el problema: permeten afegir **entrades addicionals** amb permisos per a usuaris i grups concrets.

Les ACL de Linux seguixen l'estàndard POSIX i estan disponibles en ext4, XFS, Btrfs i la majoria de sistemes d'arxius actuals. Les ordres `getfacl` i `setfacl` vénen en el paquet `acl`, instal·lat per defecte en Ubuntu (si no ho està: `sudo apt install acl`).

### Consultar una ACL: `getfacl`

```bash
getfacl /srv/projecte
```

```text
# file: srv/projecte
# owner: root
# group: dam1
# flags: -st
user::rwx
group::rwx
other::---
```

Sense entrades extra, l'ACL coincidix exactament amb els permisos UGO. Quan un fitxer té entrades addicionals, `ls -l` mostra un **`+`** al final dels permisos: `drwxrws--T+`.

### Modificar una ACL: `setfacl`

```text
setfacl [opcions] entrada fitxer
```

| Opció | Significat |
| --- | --- |
| `-m entrada` | Afig o modifica una entrada (*modify*). |
| `-x entrada` | Elimina una entrada. |
| `-b` | Elimina **totes** les entrades addicionals (torna a UGO). |
| `-R` | Recursiu. |
| `-d` | Treballa amb l'**ACL per defecte** d'un directori (la que heretaran els fitxers nous). |
| `-k` | Elimina l'ACL per defecte. |

| Format de l'entrada | Significat |
| --- | --- |
| `u:usuari:permisos` | Permisos per a un usuari concret. |
| `g:grup:permisos` | Permisos per a un grup concret. |
| `m::permisos` | Màscara (vegeu més avall). |
| `o::permisos` | Permisos de la resta. |

```bash
sudo setfacl -m u:marta:rx /srv/projecte        # marta pot entrar i llistar
sudo setfacl -m u:pablo:rwx /srv/projecte       # pablo, amb tots els permisos
sudo setfacl -m g:professors:rx /srv/projecte   # El grup professors pot llegir
getfacl /srv/projecte
```

```text
user::rwx
user:marta:r-x
user:pablo:rwx
group::rwx
group:professors:r-x
mask::rwx
other::---
```

```bash
sudo setfacl -x u:pablo /srv/projecte      # Lleva l'entrada de pablo
sudo setfacl -b /srv/projecte              # Lleva totes les entrades addicionals
```

### La màscara

En afegir entrades apareix la línia **`mask`**. La màscara definix el **màxim** de permisos que poden tindre les entrades d'usuaris concrets, de grups concrets i del grup propietari. Els permisos **efectius** d'aquestes entrades són la intersecció entre la seua entrada i la màscara:

```bash
sudo setfacl -m m::rx /srv/projecte
getfacl /srv/projecte
# user:pablo:rwx          #effective:r-x
```

Encara que `pablo` tinga `rwx`, la màscara `r-x` limita els seus permisos efectius a `r-x`.

> [!WARNING]
> En un fitxer amb ACL, `chmod g=...` **modifica la màscara**, no l'entrada `group::`. Per això, executar `chmod 750` sobre un directori amb ACL pot reduir sense que te n'adones els permisos de tots els usuaris i grups addicionals. Revisa sempre amb `getfacl` després d'utilitzar `chmod`.

### ACL per defecte (herència)

Les entrades anteriors només afecten el directori mateix. Perquè els **fitxers i subdirectoris que es creen dins** reben automàticament unes entrades, es definix una **ACL per defecte** amb `-d`:

```bash
sudo setfacl -d -m g:dam1:rwx /srv/projecte        # El que siga nou serà modificable per dam1
sudo setfacl -d -m g:professors:rx /srv/projecte   # …i llegible per professors
getfacl /srv/projecte | grep default
# default:user::rwx
# default:group::rwx
# default:group:dam1:rwx
# default:group:professors:r-x
# default:mask::rwx
# default:other::---
```

Si un directori té ACL per defecte, la `umask` **no s'aplica** al que es cree dins: els permisos els determina l'ACL per defecte. Això resol el problema del cas pràctic de l'apartat 5.4.

> [!TIP]
> Les ACL per defecte només afecten el que es cree **després**. Per a aplicar els permisos també al que ja existix, combina-les amb `-R`:
>
> ```bash
> sudo setfacl -R -m g:dam1:rwX /srv/projecte      # X majúscula: x només en directoris
> sudo setfacl -R -d -m g:dam1:rwX /srv/projecte   # (i en fitxers que ja foren executables)
> ```

### Còpies de seguretat de les ACL

```bash
getfacl -R /srv/projecte > acl-projecte.txt     # Guarda les ACL de tot l'arbre
sudo setfacl --restore=acl-projecte.txt         # Les restaura
```

En copiar amb `cp`, utilitza `cp -a` (o `cp --preserve=all`) per a conservar les ACL. Amb `tar`, afig l'opció `--acls`.

## Exercicis resolts

### Exercici 5.1. Calcular amb `umask`

Quins permisos tindran un fitxer i un directori nous amb `umask 026`? I amb `umask 037`?

{{% details "Veure solució" %}}
| `umask` | Fitxer (des de `666` = `rw-rw-rw-`) | Directori (des de `777` = `rwxrwxrwx`) |
| --- | --- | --- |
| `026` (`----w-rw-`) | `640` `rw-r-----` | `751` `rwxr-x--x` |
| `037` (`----wxrwx`) | `640` `rw-r-----` | `740` `rwxr-----` |

En cada posició s'eliminen els bits que estiguen a 1 en la màscara. Per exemple, en el fitxer amb `026`: el grup té `rw-` i la màscara lleva `w` (`2`), queda `r--`; la resta té `rw-` i la màscara lleva `rw` (`6`), queda `---`.
{{% /details %}}

### Exercici 5.2. Identificar permisos especials

Explica cada cas:

1. `-rwsr-xr-x root root /usr/bin/sudo`
2. `drwxrwsr-x root developers /srv/web`
3. `drwxrwxrwt root root /var/tmp`
4. `-rwSr--r-- ana ana notes.txt`

{{% details "Veure solució" %}}
1. **SUID** de root: `sudo` s'executa sempre amb privilegis de root, que és el que li permet canviar d'usuari després de comprovar `sudoers`.
2. **SGID** en un directori: els fitxers que es creen en `/srv/web` pertanyeran al grup `developers`.
3. ***Sticky bit***: qualsevol pot crear fitxers en `/var/tmp`, però només pot esborrar els seus.
4. **SUID sense execució** (`S` majúscula): no té cap efecte, perquè el fitxer no és executable. És un error de configuració i es corregix amb `chmod u-s notes.txt`.
{{% /details %}}

### Exercici 5.3. Directori de lliuraments

Crea `/srv/lliuraments` de manera que:

- Els membres de `dam1` puguen **deixar** fitxers, però no **llistar** el contingut del directori ni esborrar els fitxers dels companys.
- La professora `marta` puga veure i llegir-ho tot.

{{% details "Veure solució" %}}
```bash
sudo mkdir /srv/lliuraments
sudo chown marta:dam1 /srv/lliuraments
sudo chmod 1730 /srv/lliuraments    # Sticky + rwx per a marta, -wx per a dam1, res per a la resta
ls -ld /srv/lliuraments
# drwx-wx--T 2 marta dam1 ... /srv/lliuraments
```

- El grup `dam1` té `-wx`: pot **crear** fitxers (`w`) i **entrar** (`x`), però **no llistar** el directori (li falta `r`).
- El ***sticky bit*** impedix que un alumne esborre o sobreescriga el fitxer d'un altre.
- `marta`, com a propietària, té `rwx`.

Perquè `marta` puga **llegir** el contingut dels lliuraments, cada fitxer ha de tindre permís de lectura per a ella. S'aconseguix amb una ACL per defecte:

```bash
sudo setfacl -d -m u:marta:rw /srv/lliuraments
```
{{% /details %}}

### Exercici 5.4. ACL per a un cas real

En `/srv/projecte` (propietari `root`, grup `dam1`, permisos `2770`):

1. `marta` (grup `professors`) ha de poder llegir-ho tot, inclòs el que es cree en el futur.
2. `pablo` (alumne d'un altre grup) ha de poder treballar com un més de `dam1`.
3. Comprova els permisos efectius i elimina després l'accés de `pablo`.

{{% details "Veure solució" %}}
```bash
# 1. Lectura per a marta en el que existix i en el futur (X: entrar en directoris)
sudo setfacl -R -m u:marta:rX /srv/projecte
sudo setfacl -R -d -m u:marta:rX /srv/projecte

# 2. pablo amb els mateixos permisos que dam1
sudo setfacl -R -m u:pablo:rwX /srv/projecte
sudo setfacl -R -d -m u:pablo:rwX /srv/projecte

# 3. Comprovació i eliminació
getfacl /srv/projecte
sudo -u pablo touch /srv/projecte/prova_pablo      # Ha de funcionar
sudo setfacl -R -x u:pablo /srv/projecte
sudo setfacl -R -d -x u:pablo /srv/projecte
sudo -u pablo touch /srv/projecte/una_altra        # Permís denegat
```

`sudo -u pablo ordre` permet comprovar els permisos d'un altre usuari sense necessitat de conéixer la seua contrasenya.
