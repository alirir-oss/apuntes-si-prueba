# 5. Primers scripts

## 5.1 Què és un script?

Un **script** és un fitxer de **text pla** que conté una seqüència d'ordres que la shell executa l'una darrere de l'altra. Tot el que es pot escriure en el terminal es pot posar en un script, i a més Bash ofereix elements propis d'un llenguatge de programació: variables, condicions, bucles i funcions.

Per a què serveixen? Per a **automatitzar** tasques repetitives o propenses a errors: preparar un entorn de desenvolupament, fer còpies de seguretat, desplegar una aplicació, processar fitxers de registre, donar d'alta usuaris…

| | Programa compilat (Java, C…) | Script de Bash |
| --- | --- | --- |
| Execució | Es tradueix abans (compilació) a codi màquina o *bytecode*. | Un **intèrpret** (`bash`) llig i executa les línies una a una. |
| Errors | Molts es detecten en compilar. | Es detecten en arribar a la línia amb l'error, en temps d'execució. |
| Punt fort | Rendiment, programes grans. | "Apegar" programes existents i automatitzar el sistema. |

> [!NOTE]
> Bash és ideal per a scripts d'unes desenes o pocs centenars de línies que combinen ordres del sistema. Si el problema requereix estructures de dades complexes o molt de càlcul, és millor un llenguatge de propòsit general com Python.

## 5.2 El nostre primer script

{{% steps %}}
1. ## Crear el fitxer

   Utilitza qualsevol editor de text pla: `nano`, `vim` o VS Code. Per convenció, els scripts de shell porten l'extensió `.sh` (Linux no la necessita, però ajuda a identificar-los).

   ```bash
   mkdir -p ~/scripts && cd ~/scripts
   nano hola.sh
   ```

2. ## Escriure el contingut

   ```bash
   #!/bin/bash
   # hola.sh - El meu primer script
   # Mostra una salutació i algunes dades del sistema

   echo "Hola, $USER!"
   echo "Hui és $(date +%d/%m/%Y) i estàs en l'equip $(hostname)."
   echo "El teu directori actual és: $(pwd)"
   ```

   En `nano` es guarda amb `Ctrl+O` i s'ix amb `Ctrl+X`.

3. ## Donar permís d'execució

   ```bash
   chmod u+x hola.sh     # o chmod 755 hola.sh
   ```

4. ## Executar-lo

   ```bash
   ./hola.sh
   ```

   ```text
   Hola, alumno!
   Hui és 08/11/2026 i estàs en l'equip dam-pc.
   El teu directori actual és: /home/alumno/scripts
   ```
{{% /steps %}}

### La primera línia: el *shebang*

La línia `#!/bin/bash` s'anomena ***shebang*** (pels caràcters `#` *sharp* i `!` *bang*). Ha de ser **la primera línia** del fitxer, sense espais davant, i indica al sistema quin intèrpret ha d'executar l'script.

| *Shebang* | Ús |
| --- | --- |
| `#!/bin/bash` | Executar amb Bash. És el que utilitzarem en aquesta unitat. |
| `#!/usr/bin/env bash` | Busca `bash` en el `PATH`. Més portable (per exemple, en macOS amb Bash instal·lat a banda). |
| `#!/bin/sh` | Shell POSIX mínima (en Debian/Ubuntu és `dash`). **No** admet moltes característiques de Bash com `[[ ]]` o els *arrays*. |
| `#!/usr/bin/env python3` | El mateix mecanisme serveix per a altres llenguatges interpretats. |

### Comentaris

Tot el que segueix una `#` (excepte el *shebang*) és un **comentari** i Bash l'ignora. Utilitza'ls per a explicar **per què** es fa alguna cosa, no per a repetir el que ja diu el codi.

```bash
# Comentari de línia completa
echo "Hola"   # Comentari al final d'una línia
```

## 5.3 Maneres d'executar un script

| Forma | Necessita `chmod +x`? | Utilitza el *shebang*? | On s'executa |
| --- | --- | --- | --- |
| `./hola.sh` | Sí | Sí | En una shell **nova** (subprocés). |
| `bash hola.sh` | No | No (es força Bash) | En una shell nova. |
| `hola.sh` (sense ruta) | Sí | Sí | Només funciona si el directori està en el `PATH`. |
| `source hola.sh` o `. hola.sh` | No | No | En la **shell actual**: les variables i els canvis de directori es mantenen en acabar. |

Per què cal escriure `./` davant? Perquè, per seguretat, la shell només busca les ordres en els directoris de la variable `PATH`, i el directori actual no hi està inclòs. `./` indica explícitament "el fitxer `hola.sh` d'aquest directori".

Per a poder executar els teus scripts des de qualsevol lloc, guarda'ls en `~/.local/bin`, un directori que les distribucions actuals afigen al `PATH` automàticament si existeix:

```bash
mkdir -p ~/.local/bin
cp hola.sh ~/.local/bin/hola     # Es pot llevar l'extensió
# Si no hi era, tanca i obri el terminal (o executa: source ~/.profile)
hola                             # Ja funciona com qualsevol altra ordre!
echo "$PATH"                     # Directoris on es busquen les ordres
```

> [!WARNING]
> **Scripts creats en Windows.** Windows acaba les línies amb dos caràcters (`\r\n`, CRLF) i Linux amb un (`\n`, LF). Un script amb finals CRLF falla amb errors estranys com `/bin/bash^M: bad interpreter` o `$'\r': command not found`. Solució: en VS Code, fes clic en `CRLF` en la barra d'estat i canvia-ho a `LF`; o corregeix el fitxer amb `sed -i 's/\r$//' script.sh` (o `dos2unix script.sh`).

## 5.4 Codi d'eixida: `exit`

Tota ordre, en acabar, retorna al sistema un número entre 0 i 255 anomenat **codi d'eixida** (*exit status*):

- `0` significa **èxit**.
- Qualsevol altre valor indica **error** (cada programa documenta el significat dels seus codis).

El codi de l'última ordre es guarda en la variable especial `$?`. En els nostres scripts el fixem amb `exit`:

```bash
ls /etc > /dev/null
echo $?          # 0  -> correcte
ls /noexiste
echo $?          # 2  -> error (ls utilitza 2 per a "problema greu")
```

```bash
#!/bin/bash
# comprobar_red.sh - Acaba amb 0 si hi ha connexió a Internet i amb 1 si no
if ping -c 1 -W 2 8.8.8.8 > /dev/null 2>&1; then
    echo "Connexió correcta"
    exit 0
else
    echo "Sense connexió" >&2     # >&2 envia el missatge a l'eixida d'errors
    exit 1
fi
```

Si un script no executa `exit`, el seu codi d'eixida és el de l'última ordre executada. Un bon script retorna sempre un codi que reflectisca si ha complit la seua tasca, perquè altres scripts (o eines com `cron` o un *pipeline* de CI) puguen saber-ho.

## 5.5 Depurar scripts

Quan un script no fa el que esperem, tenim diverses eines:

| Eina | Ús |
| --- | --- |
| `bash -n script.sh` | Comprova la **sintaxi** sense executar res. |
| `bash -x script.sh` | Executa mostrant cada ordre (precedida de `+`) **després** de substituir les variables. És l'eina de depuració més útil. |
| `set -x` … `set +x` | Activa i desactiva la traça només en una part de l'script. |
| `echo "DEBUG: var=$var" >&2` | Missatges de depuració per l'eixida d'errors. |
| **ShellCheck** | Analitzador que detecta errors típics i males pràctiques. Instal·la'l amb `sudo apt install shellcheck` o com a extensió de VS Code. |

```bash
bash -x hola.sh
```

```text
+ echo 'Hola, alumno!'
Hola, alumno!
++ date +%d/%m/%Y
++ hostname
+ echo 'Hui és 08/11/2026 i estàs en l'\''equip dam-pc.'
…
```

> [!TIP]
> Acostuma't a passar **ShellCheck** a tots els teus scripts (`shellcheck script.sh`). Cada avís té un codi (per exemple `SC2086`) que es pot buscar en <https://www.shellcheck.net/wiki/> amb una explicació detallada.

## 5.6 Mode estricte

Per defecte, Bash és molt permissiu: si una ordre falla, **continua** amb la següent; i si utilitzem una variable que no existeix, la substitueix per una cadena buida sense avisar. Això pot provocar desastres. Molts scripts professionals comencen amb:

```bash
#!/bin/bash
set -euo pipefail
```

| Opció | Efecte |
| --- | --- |
| `-e` (*errexit*) | L'script es deté si una ordre falla (retorna un codi distint de 0). |
| `-u` (*nounset*) | Utilitzar una variable no definida és un error. |
| `-o pipefail` | Una canonada falla si falla **qualsevol** de les seues ordres, no només l'última. |

```bash
#!/bin/bash
set -euo pipefail
DIR_TRABAJO="/tmp/mi_app"
cd "$DIR_TRABAJO"            # Si el directori no existeix, l'script es deté ací…
rm -rf ./*                   # …i mai arriba a esborrar el contingut del directori equivocat
```

> [!NOTE]
> `set -e` té excepcions (no s'aplica, per exemple, a les ordres utilitzades com a condició en un `if` o abans de `&&`/`||`). És una xarxa de seguretat, no un substitut de comprovar els errors de les operacions importants.

## 5.7 Plantilla i bones pràctiques

Aquesta plantilla arreplega les bones pràctiques que anirem aplicant en els apartats següents:

```bash
#!/bin/bash
#==============================================================
# Nom:         nombre_script.sh
# Descripció:  Què fa l'script, en una o dues línies.
# Ús:          ./nombre_script.sh <argument1> [argument2]
# Autor:       Nom Cognom
# Data:        2026-11-08
#==============================================================
set -euo pipefail

# --- Constants i configuració ---------------------------------
readonly LOG="/tmp/nombre_script.log"

# --- Funcions -------------------------------------------------
uso() {
    echo "Ús: $0 <argument1> [argument2]" >&2
    exit 1
}

# --- Programa principal ---------------------------------------
[[ $# -ge 1 ]] || uso      # Comprovació d'arguments (apartats 6 i 7)

echo "Processant $1…" | tee -a "$LOG"
exit 0
```

**Bones pràctiques:**

1. *Shebang* en la primera línia i capçalera que explique què fa l'script i com s'utilitza.
2. Noms de variables i funcions **descriptius**.
3. Variables **sempre entre cometes dobles**: `"$fichero"` (ho veurem en l'apartat 6).
4. Comprovar els arguments i les condicions prèvies (que existisquen els fitxers, que es tinguen permisos…) abans d'actuar.
5. Missatges d'error clars, enviats a l'eixida d'errors (`>&2`), i codis d'eixida coherents.
6. Provar primer en un entorn segur (un directori de proves o un contenidor), sobretot si l'script esborra o modifica fitxers.
7. Passar **ShellCheck** i sagnar el codi perquè es llija amb facilitat.

## Exercicis resolts

### Exercici 5.1. Fitxa del sistema

Crea l'script `ficha.sh` que mostre, amb un títol i una línia per dada: l'usuari, el nom de l'equip, la distribució, la versió del *kernel*, el temps encés i l'espai lliure en `/`.

{{% details "Veure solució" %}}
```bash
#!/bin/bash
# ficha.sh - Mostra una fitxa resum del sistema

echo "===== FITXA DEL SISTEMA ====="
echo "Usuari:        $(whoami)"
echo "Equip:         $(hostname)"
# /etc/os-release defineix la variable PRETTY_NAME; la carreguem amb source en una subshell
echo "Distribució:   $(. /etc/os-release && echo "$PRETTY_NAME")"
echo "Kernel:        $(uname -r)"
echo "Encés:         $(uptime -p)"
echo "Lliure en /:   $(df -h / | awk 'NR == 2 { print $4 }')"
echo "============================="
```

```bash
chmod +x ficha.sh
./ficha.sh
```
{{% /details %}}

### Exercici 5.2. Trobar l'error

Aquest script hauria de mostrar la data, però en executar-lo amb `./fecha.sh` apareix `Permission denied`; després de solucionar-ho, apareix `fecha: command not found`. Explica i corregeix tots dos errors.

```bash
#!/bin/bash
fecha = $(date +%F)
echo "Hui és $fecha"
```

{{% details "Veure solució" %}}
1. **`Permission denied`**: el fitxer no té permís d'execució. Es corregeix amb `chmod u+x fecha.sh`.
2. **`fecha: command not found`**: en Bash **no hi pot haver espais** al voltant de l'`=` en una assignació. Amb espais, Bash interpreta `fecha` com una ordre a la qual es passen els arguments `=` i `2026-11-08`.

```bash
#!/bin/bash
fecha=$(date +%F)
echo "Hui és $fecha"
```

Amb `bash -x fecha.sh` hauríem vist la línia `+ fecha = 2026-11-08`, que delata el problema. ShellCheck també el detecta i proposa la correcció.
{{% /details %}}

### Exercici 5.3. `./script` enfront de `source script`

Crea `ir_tmp.sh` amb el contingut següent i executa'l de les dues maneres. En quin directori et trobes després de cadascuna? Per què?

```bash
#!/bin/bash
cd /tmp
echo "Dins de l'script estic en: $(pwd)"
```

{{% details "Veure solució" %}}
```bash
chmod +x ir_tmp.sh
./ir_tmp.sh      # Dins de l'script estic en: /tmp
pwd              # /home/alumno/scripts -> no hem canviat!
source ir_tmp.sh # Dins de l'script estic en: /tmp
pwd              # /tmp -> ara sí
```

Amb `./ir_tmp.sh` l'script s'executa en un **procés fill**: el `cd` canvia el directori d'aquest procés, que desapareix en acabar. Amb `source`, les ordres s'executen en la **shell actual**, així que el canvi es manté. Per això els fitxers de configuració com `~/.bashrc` es carreguen amb `source`.
{{% /details %}}
